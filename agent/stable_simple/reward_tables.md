# Reward Function Analysis

## Formula

From [environment.py](file:///Users/fauzanghaza/Documents/code/kubernetes-autoscaling/agent/stable_simple/environment/environment.py#L15-L31):

```python
rt_penalty = response_time / 100.0
cost = action / 99.0
reward = (1.0 - rt_penalty) * (1.0 - cost)
```

| Parameter | Range | Description |
|-----------|-------|-------------|
| `action` | 0 – 99 (discrete) | Scaling action from `Discrete(100)` |
| `response_time` | 0 – 300 (%) | Percentage of `max_response_time` (SLA target), capped at 300% |
| `rt_penalty` | 0.0 – 3.0 | Response time penalty (`response_time / 100`) |
| `cost` | 0.0 – 1.0 | Resource cost (`action / 99`) |
| [reward](file:///Users/fauzanghaza/Documents/code/kubernetes-autoscaling/agent/stable_simple/environment/environment.py#257-269) | -2.0 – 1.0 | Final reward value |

> [!IMPORTANT]
>
> `response_time` is a **percentage of `max_response_time`** (the SLA target), computed in
> [metrics.py](file:///Users/fauzanghaza/Documents/code/kubernetes-autoscaling/agent/stable_simple/utils/metrics.py#L128-L129)
> as `(actual_rt / max_response_time) × 100`, capped at 300%.
>
> - **Reward = 0** when `response_time = 100%` (RT equals SLA target) OR `action = 99`
> - **Reward > 0** when `response_time < 100%` (RT below SLA target) AND `action < 99`
> - **Reward < 0** when `response_time > 100%` (RT exceeds SLA target, penalty grows with lower action)
> - **Max reward = 1.0** at `action=0, response_time=0%`

---

## Mathematical Analysis of the Reward Function

### Factor Decomposition

The reward is a **product of two independent factors**:

```
reward = Factor_A × Factor_B
```

Where:

- **Factor A** = `(1 - response_time / 100)` → measures **performance quality** (RT as % of SLA target)
- **Factor B** = `(1 - action / 99)` → measures **resource efficiency**

| Factor | Input | Range | Meaning |
|--------|-------|-------|---------|
| Factor A | RT = 0% | **+1.0** | Perfect performance (no latency) |
| Factor A | RT = 100% | **0.0** | RT equals SLA target (boundary) |
| Factor A | RT = 300% | **-2.0** | RT is 3× the SLA target (worst, capped) |
| Factor B | action = 0 | **+1.0** | Most efficient (fewest replicas) |
| Factor B | action = 50 | **+0.495** | Mid-range |
| Factor B | action = 99 | **0.0** | Least efficient (most replicas) |

Because the reward is multiplicative, the **sign and magnitude** of the final reward depends
entirely on the interaction between these two factors.

### The Four Reward Regions

| Region | Condition | Factor A | Factor B | Reward | Meaning |
|--------|-----------|----------|----------|--------|---------|
| ✅ **Positive** | RT < 100% AND action < 99 | > 0 | > 0 | **> 0** | RT below SLA + efficient resources |
| 🟰 **Zero** | RT = 100% OR action = 99 | = 0 or any | any or = 0 | **= 0** | Either factor zeroes out the product |
| ❌ **Negative** | RT > 100% AND action < 99 | < 0 | > 0 | **< 0** | RT exceeds SLA, and still saving resources |
| 🟰 **Zero (special)** | RT > 100% AND action = 99 | < 0 | = 0 | **= 0** | RT exceeds SLA, but max cost neutralizes penalty |

### Detailed Justification for Key Scenarios

#### 1. Best Case: `action=0, RT=0%` → reward = **+1.0** (highest)

```
Factor A = (1 - 0/100)  = (1 - 0.0) = +1.0   ← perfect performance (0% of SLA)
Factor B = (1 - 0/99)   = (1 - 0.0) = +1.0   ← maximum efficiency
reward   = (+1.0) × (+1.0) = +1.0
```

**Why this is the highest**: The agent achieved **zero response time** (0% of SLA target)
while using the **minimum replicas** (action=0). Both factors are at their maximum (+1.0),
so the product is maximized. This is the ideal behavior — fast service with minimal cost.

#### 2. Worst Case: `action=0, RT=300%` → reward = **-2.0** (lowest)

```
Factor A = (1 - 300/100) = (1 - 3.0) = -2.0   ← worst performance penalty
Factor B = (1 - 0/99)    = (1 - 0.0) = +1.0   ← maximum efficiency multiplier
reward   = (-2.0) × (+1.0) = -2.0
```

**Why this is the lowest**: Factor A is at its most negative (-2.0) because RT is at the
maximum (300% of SLA target — 3× the allowed response time). Factor B is at its maximum
(+1.0) because action=0 means zero cost. Since Factor B is +1.0, it applies the **full
magnitude** of the negative Factor A without any dampening. The agent is being maximally
punished because:

- ❌ It delivered the **worst possible performance** (RT = 3× SLA target)
- ❌ While using the **fewest resources** (action=0), meaning it didn't even try to fix the problem

**Why not action=99 with RT=300?** Because action=99 makes Factor B = 0.0, which **zeroes
out** everything:

```
Factor A = (1 - 300/100) = -2.0
Factor B = (1 - 99/99)   = 0.0
reward   = (-2.0) × (0.0) = 0.0   ← penalty neutralized!
```

Even though RT=300 is terrible, the maximum resource usage (action=99) completely neutralizes
the penalty. This is a mathematical consequence of multiplication by zero — no matter how
negative Factor A is, multiplying by zero gives zero.

#### 3. Zero Boundary: `any action, RT=100%` → reward = **0.0**

```
Factor A = (1 - 100/100) = (1 - 1.0) = 0.0   ← RT exactly equals SLA target
Factor B = (1 - action/99) = any value         ← doesn't matter
reward   = (0.0) × (anything) = 0.0
```

**Why RT=100% is the zero boundary**: When `response_time = 100%`, the actual RT equals
exactly the `max_response_time` (SLA target). The `/100.0` divisor converts the percentage
back to a ratio, so `rt_penalty = 1.0` and `Factor A = 0`. Below 100% (RT under SLA target),
rewards are positive. Above 100% (RT exceeds SLA target), rewards become negative. This
threshold is **not hardcoded to a specific latency** — it adapts to whatever `max_response_time`
is configured.

#### 4. High Action Dampening: `action=90, RT=300%` → reward = **-0.182**

```
Factor A = (1 - 300/100) = -2.0               ← RT is 3× SLA target
Factor B = (1 - 90/99)   = (1 - 0.909) = +0.091
reward   = (-2.0) × (+0.091) = -0.182
```

Compare with action=0, RT=300 → reward = -2.0. The penalty is **reduced by 91%** (from -2.0
to -0.182) simply because the high action shrinks Factor B close to zero. This means:

- When RT is bad, **using more replicas reduces the punishment**
- The cost factor acts as a **dampener** on the RT penalty

#### 5. Symmetric Trade-off: same reward from different combinations

Two different (action, RT) pairs can produce similar rewards:

```
action=0,  RT=50%  → (1 - 0.5) × (1 - 0.0)   = 0.5 × 1.0   = 0.500
action=50, RT=0%   → (1 - 0.0) × (1 - 0.505)  = 1.0 × 0.495 = 0.495
```

These are nearly equal (~0.5), showing the **trade-off**: you can achieve a similar reward by
either having RT at 50% of SLA with minimum replicas, or perfect RT with moderate replicas.

### How Factor B (action) Scales the RT Penalty

When RT > 100% (exceeds SLA target), Factor A is negative. Factor B determines **how much of that penalty is felt**:

| Action | Factor B `(1-a/99)` | RT=150% penalty | RT=200% penalty | RT=300% penalty |
|-------:|---------------------:|---------------:|---------------:|---------------:|
| 0 | 1.000 (full penalty) | -0.500 | -1.000 | **-2.000** |
| 20 | 0.798 | -0.399 | -0.798 | -1.596 |
| 50 | 0.495 | -0.247 | -0.495 | -0.990 |
| 80 | 0.192 | -0.096 | -0.192 | -0.384 |
| 99 | 0.000 (no penalty) | 0.000 | 0.000 | **0.000** |

**Pattern**: As action increases, Factor B shrinks toward 0, which proportionally reduces the
magnitude of any negative (or positive) reward. At action=99, Factor B = 0, making the reward
always 0 regardless of RT.

### Why the Multiplicative Design Matters

> [!NOTE]
> The multiplicative structure `(1 - RT/100) × (1 - action/99)` creates a **coupled**
> optimization problem. The agent cannot optimize one factor independently — both performance
> and resource efficiency must be balanced simultaneously.
>
> - **Low action + low RT** → high positive reward (efficient AND fast)
> - **Low action + high RT** → large negative reward (cheap BUT slow = worst outcome)
> - **High action + low RT** → small positive reward (fast BUT expensive = wasted resources)
> - **High action + high RT** → near-zero reward (expensive AND slow, but penalty is dampened)
>
> This design naturally pushes the RL agent toward the **optimal balance**: use just enough
> replicas to keep response time below the SLA target (100%), but no more than necessary.
